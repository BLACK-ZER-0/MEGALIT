## 🚨 Reporting a Security Vulnerability

If you discover a security vulnerability within **MEGALIT** itself (e.g., code execution flaws, dependency vulnerabilities, unhandled active probe leaks), please report it responsibly.

### How to Report

1. **Do NOT open a public GitHub issue** for undisclosed security vulnerabilities.
2. Contact the maintainer directly via GitHub or create a **Private Vulnerability Report** through the repository’s **Security** tab (`Security -> Advisories -> Report a vulnerability`).
3. Include as much detail as possible:
   * Description of the vulnerability.
   * Steps to reproduce the issue safely.
   * Potential impact (e.g., Denial of Service, Remote Code Execution, Data Leakage).
   * Any proof of concept (PoC) code or logs (with sensitive target information redacted).

### Response Timeline

* **Initial Acknowledgment:** Within **48 hours** of receiving the report.
* **Status Update & Assessment:** Within **5 business days**.
* **Fix & Release:** We aim to patch critical security flaws within **14 business days** and issue a security release advisory.

## 🔐 Best Practices for Users

When running **MEGALIT** in production or sensitive security environments:

* **Use Proxies Responsibly:** When using `--proxy`, ensure your proxy providers are trusted and do not leak request data or sensitive headers.
* **Custom Signatures (`--user-list` / `--user-vendors-list`):** Validate all custom signatures before loading them into Megalit to avoid potential regular expression Denial of Service (ReDoS) or unintended execution.
* **Log Confidentiality:** Log files generated by Megalit (`logs/megalit_*.log`) may contain raw HTTP headers, cookies, and network infrastructure data. Keep these log files secure and ensure they are deleted or anonymized before sharing.
